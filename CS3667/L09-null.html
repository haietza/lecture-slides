Null Object

  • Raise your hand if you've ever seen a NullPointerException.
  • It happens frequently: Some reference that was supposed to point to a real object is instead pointing at nothing, and the first line of code that tries to use it blows up.

Null Pointer Exception

						
							void foo(Blah b) {
								b.yada();
							}
  • The obvious fix is the null guard; check before you call.
  • And it works, but the problem is scale.
  • It only takes one developer forgetting one guard, one time, to bring the crash back.
  • We're solving a correctness problem with something that depends on everyone remembering, forever.
  • That should feel fragile; the same instinct that got us to Strategy and Singleton: if a design depends on every caller doing the right thing by memory, the design is asking to fail.

The Standard Fix

						
							void foo(Blah b) {
								if (b != null) {
									b.yada();
								}
							}

Guard clauses work, but:

  • Every caller has to remember to write the guard.
  • One missed guard anywhere in the codebase reintroduces the crash.
  • Linked structures (lists, trees) end up covered in these checks.
  • If we can guarantee that Blah b is an object, we can eliminate the guard.

A Better Fix

  • What if Blah b was guaranteed to be either:
    • An actual Blah object reference (that could call yada()), or
    • A special object reference (that would do nothing)
  • Two things have to happen:
    • A Blah NullObject object is needed to pass to foo()
    • The client code needs to use this NullObject instead of just null
  • Head First doesn't give the Null Object a full chapter (it's an 'honorable mention' tucked into the Command chapter).

The Null Object

A Null Object is a stand-in used when there's no meaningful object to return, so the responsibility for handling the missing case moves off the client and onto the object itself.

— paraphrased from Head First Design Patterns
  • It can be built on an abstract class or an interface.
  • The Null Object implementation overrides the methods in "safe" and "nullish" ways.
  • The key idea is always the same: The client only ever talks to the abstract type, so it can never tell (and never needs to tell) whether it's holding the real implementation or the null one.
  • All client code using Blah will need to be examined. Where it is using null references, it now needs to use the Blah Null Object.

The Structure

						
							public interface Blah {
								void operation();
							}

							public class RealBlah implements Blah {
								@Override
								public void operation() {
									System.out.println("doing the real thing");
								}
							}

							public class NullBlah implements Blah {
								@Override
								public void operation() {
									// does nothing
								}
							}
  • Three classic uses, plus a fourth one that should look very familiar: any time you've got a Strategy-style field that might not be set yet — like a VideoRenderBehavior before a VideoClip knows how it should render — a Null Object is a natural default.

In Practice

  • Placeholders in collections: Loop through an array calling methods on every element, with no "is this slot empty" check.
  • Terminators in linked structures: A list or tree's null object safely ends recursion instead of crashing on it.
  • Borders in 2-D grids: Image-processing or cellular-automata code that needs "virtual" neighbor cells at the edges of a grid.
  • Default strategies: A Strategy field (sound familiar?) that hasn't been assigned a real behavior yet can default to a do-nothing strategy instead of null.
  • Null Object is elegant when the 'do nothing' behavior is obvious and safe.
  • It gets shaky when there's no honest neutral value.
  • area() returns a value, not a void
  • Java forces us to commit to some double, so unlike NullBlah.operation(), there is no "do nothing" option; we're always choosing a stand-in value, and that choice carries risk the void case doesn't have.
  • 0.0 looks safe because it's neutral for addition (sum()), but it's not neutral for comparison (min()/max() logic); so "safe" for a query-returning null object is context-dependent, not guaranteed the way it is for a no-op command.
  • Don't force the pattern where a real null check, or a different design entirely, is actually the clearer answer.

Honest Caveat

Not every method can do nothing safely.

  • A linked list's length() → Null Object returns 0.
  • A polygon's area() → What would a "null polygon" honestly return?
