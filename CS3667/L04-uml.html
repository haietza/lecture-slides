Unified Modeling Language

  • Why do we model software?
  • The problem of complexity
  • Physical systems have natural models (like a car engine schematic)
  • But software is abstract and invisible; you cannot see or touch it

Modeling Software

  • A car engine has ~200 moving parts; we use diagrams to understand it.
  • An ATM system has thousands of interacting objects; we need models even more.
  • Software is invisible and abstract; you cannot see or touch it.
  • Models make software visible, discussable, and understandable.
  • Every model belongs to one of three perspectives

Unified Modeling Language (UML)

  • The industry-standard visual language for specifying, constructing, and documenting software systems.
  • The Three System Perspectives:
    • Functional Behavior
    • Static Structure
    • Dynamic Behavior
  • Functional perspective asks 'what?', view from the outside

Functional Perspective

  • What does the system do?
  • Why does someone use it?
  • Use Case Diagram, Activity Diagram
  • Static perspective asks 'with what?', what are the building blocks

Static Perspective

  • What objects are involved?
  • What are their attributes?
  • What operations do they perform?
  • How are they related to each other?
  • Class Diagram, Object Diagram
  • Dynamic perspective asks 'how?', what happens at runtime

Dynamic Perspective

  • How do objects interact over time?
  • Sequence/State Diagram, Activity Diagram
  • Functional: A customer withdraws money from an account
  • Static: A `Customer` object has an `Account` object
  • Dynamic: When withdraw() is called, the system checks the Account balance before deducting money for the Customer

  • For large systems, it can be useful to categorize similar things.
  • Problem: If we put UI, business logic, and data in one class, our system becomes a fragile "God Class."
  • Solution (BEC): Categorize our classes into three types.

The BEC Taxonomy

  • For software systems, we can categorize our classes:
    • Boundary: Interfaces with actors
    • Control: Implements system logic and coordinates tasks
    • Entity: Stateful objects containing system information
  • The Golden Rule: Boundaries NEVER talk directly to Entities. All communication goes through Control objects.

Boundary Objects

  • Inside our system, but interface with elements outside the system.
  • They are a "portal" or "gateway" between outside and inside.
  • Accepting a card requires writing specific command bit patterns to device driver memory locations (turn on the rollers to accept a card).
  • Initiating that command requires a second write to a separate memory location (to initiate that command request).
  • This is hardware-protocol logic; volatile, vendor-specific, and completely irrelevant to your business logic.
  • The CardReader object is inside our system, but up against the boundary acting as a conduit to the outside world device.

Boundary Objects: CardReader Example

  • The Problem: Hardware devices speak a low-level language your application should never have to know.
  • The Solution: Wrap it in a Boundary Object.

					// The rest of the system never sees device registers or bit patterns.
					// It only knows one thing:
					cardReader.acceptCard();

Entity Objects

  • Represent information, data, and state needed by the system; not boundary objects.
  • They are not just data containers; they provide methods that act on their own data.
  • When your ATM transaction is completed, you get a receipt printed out.
  • The Receipt is not a boundary object. It never touches anything external.
  • As you progress through the transation, we build up this entity object.
  • Its entire job is to accumulate and hold the meaningful data that represents a completed transaction.
  • That’s the hallmark of an entity object: it models something real and stateful within your business domain.

Entity Objects: Receipt Example

  • The printer is a boundary object, but the receipt is likely an entity object.
  • The Receipt Entity is build up incrementally.

					// State accumulates as the transaction progresses
					receipt.setDateTime(LocalDateTime.now());
					receipt.setAccountNumber(account.getAccountNumber());
					receipt.setFinalBalance(account.getBalance());

					// The Entity is passed to Boundary objects as needed
					printer.print(receipt);      // Output to hardware
					transactionLog.archive(receipt); // Output to local storage
  • Control objects manage behavior; they coordinate the other objects so neither entity nor boundary objects have to.

Control Objects

  • Orchestrate the flow and manage behavior.
  • Coordinate the other objects so neither entity nor boundary objects have to interact directly.
  • One main controller initializes everything; separate controllers per major use case.
  • The AtmController object instantiates boundary objects.
  • Its main menu would create a WithdrawCashController object when the user indicates they want to make a withdrawal.
  • The WithdrawCashController object manages the flow of the transation.
  • When the transation is complete, the WithdrawCashController object is done an not re-used.
  • A subsequent withdrawal will get a new WithdrawCashController object, you cannot accidentally carry a balance from one withdrawal into the next.

Control Objects: ATM Example

  • Application Scope vs. Transaction Scope:
    • AtmController: Handles system startup, main menus, and hardware initialization; lives until the ATM shuts down.
    • WithdrawCashController: Manages a single withdrawal flow; created dynamically and destroyed when transaction finishes.
  • Architectural Value: Each transaction gets its own controller, state, and lifecycle, ensuring no shared mutable state between transactions.

Use Case Diagrams

A Use Case diagram answers the question: "What does this system do for whom?"

  • High-level view, no implementation details
  • Shows the services a system provides and who uses them
  • Starting point for every other model
  • Primary actors are on the left; they initiate the interaction.
  • Secondary actors are on the right; they react to the interaction.
  • Actors are not part of the system.
  • What do these use cases share?
  • They all need to authenticate the user.
  • In software, we hate duplication.
  • So we factor out the common steps into another use case with a different relationship.

Use Case Diagrams

  • Actors (Stick Figures): External entities interacting with the system.
  • Use Cases (Ovals): Major system functionalities, start with a verb.
  • Relationships:
    • Association (Solid Line): Connects an actor to a use case.
A use case diagram showing the Customer on the left with interaction lines to use cases Login to App, Check Balance, and Transfer Funds, which are all contained in the System. The Bank is on the right with interaction lines to Check Balance and Transfer Funds.
  • Think of it as the base case reaches out to grab the included behavior.
  • The arrow direction says WithdrawCash calls Authenticate.
  • Typically returns back to originating use case.

Relationships: Include

Always happens (dotted line)

  • Arrow points FROM base case TO included case.
  • Models mandatory sub-behavior factored out to eliminate duplication.
  • Example: Every transaction always includes Authentication.
  • Think of it as the exception is extneding or adding to the base.
  • NSF -> WithdrawCash, the exception hangs off the base.
  • May not return to originating use case.

Relationships: Extend

Sometimes happens (dotted line)

  • Arrow points FROM extending case TO base case.
  • Models exceptional flows that may or may not occur.
  • Example: WithdrawCash may extend with "Non-Sufficient Funds".

Relationships: Generalization

Generalization (Solid Arrow with Open Triangle): Is a kind of

  • Similar to abstract classes.
  • Child use case (or actor) is a specialized version of the parent.
  • Arrow goes FROM child TO parent.
  • Example: Transfer to Another Account IS A kind of Transfer Funds.

Include and Extend

  • Login to App is base use case
  • Verify Password is the included use case (always happens)
  • Display Login Erro is the extended use case (sometimes happens)

Generalization

  • Adult Customer and Minor Customer are child actors of Customer
  • Transfer Funds is the generalized or parent use case. Transfer to Another Account and Transfer to Another User are specialized use cases, children of Transfer Funds.

Class Diagrams

  • Divided into three compartments:
    • Name
    • Attributes/State
    • Operations/Behavior
  • Visibility modifiers:
    • + Public
    • - Private
    • # Protected
  • Cat is an abstract class with private fields and public methods. It implements the Hunter interface.
  • Barn Cat is a class that inherits from Cat. It has an association guards Barn.
  • Barn is a class with a composition relationship to the Stall class where one Barn contains zero to many Stalls.
  • Lion is a class that inherits from Cat with an aggregation relationship to the Pride class, seen in the lions field, which is a list of Lion objects.
  • Color is an enumeration used in Barn.

  • Include all 3 classes: Customer, ATM, Account.

  • Draw association lines between classes where appropriate.
  • If a Class Diagram is the architectural blueprint of a house, an Object Diagram is a photograph of a specific room on a Tuesday afternoon.
  • It shows us exactly what is happening in memory at runtime.
  • While you will draw Class Diagrams for almost every project, you only pull out Object Diagrams when you need to understand a very specific, complex state.
  • Data structures like linked lists, trees, or intricate design patterns.

Object Diagrams

  • Focus on concrete instances of objects (vs. class definitions).
  • Capture the state of a system object and its relationships at a specific moment in time.
  • Used less frequently than Class Diagrams.
  • Useful for depicting an isolated part of a complex system.
  • Often used to visualize the current state of complex data structures.
