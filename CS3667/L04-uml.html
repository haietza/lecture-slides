Unified Modeling Language

  • Why do we model software?
  • The problem of complexity
  • Physical systems have natural models (like a car engine schematic)
  • But software is abstract and invisible; you cannot see or touch it

Modeling Software

  • A car engine has ~200 moving parts; we use diagrams to understand it.
  • An ATM system has thousands of interacting objects; we need models even more.
  • Software is invisible and abstract; you cannot see or touch it.
  • Models make software visible, discussable, and understandable.
  • Every model belongs to one of three perspectives

Unified Modeling Language (UML)

  • The industry-standard visual language for specifying, constructing, and documenting software systems.
  • The Three System Perspectives:
    • Functional Behavior
    • Static Structure
    • Dynamic Behavior
  • Functional perspective asks 'what?', view from the outside

Functional Perspective

  • What does the system do?
  • Why does someone use it?
  • Use Case Diagram, Activity Diagram
  • Static perspective asks 'with what?', what are the building blocks

Static Perspective

  • What objects are involved?
  • What are their attributes?
  • What operations do they perform?
  • How are they related to each other?
  • Class Diagram, Object Diagram
  • Dynamic perspective asks 'how?', what happens at runtime

Dynamic Perspective

  • How do objects interact over time?
  • Sequence/State Diagram, Activity Diagram
  • Functional: A customer withdraws money from an account
  • Static: A `Customer` has an `Account`
  • Dynamic: When withdraw() is called, the system checks the Account balance before deducting money for the Customer

Use Case Diagrams

A Use Case diagram answers the question: "What does this system do for whom?"

  • High-level view, no implementation details
  • Shows the services a system provides and who uses them
  • Starting point for every other model
  • Primary actors are on the left; they initiate the interaction.
  • Secondary actors are on the right; they react to the interaction.
  • Actors are not part of the system.

Use Case Diagrams

  • Actors (Stick Figures): External entities interacting with the system.
  • Use Cases (Ovals): Major system functionalities, start with a verb.
  • Relationships:
    • Association (Solid Line): Connects an actor to a use case.

  • The next step in our modeling is to dive deeper into each use case by considering an activity diagram.
  • Activity diagrams are another way we model the functional perspective (what does the system do, what happens in the system).
  • They actually straddle functional (documenting workflows and use case flows) and dynamic (showing control flow during execution).
  • But we will study them here, since they show what happens, not who does it, slightly different from some dynamic perspective models we will explore.
  • Diamonds are your if-statements made visual.
  • Always label both paths out of a diamond — typically something like [yes]/[no] or [valid]/[invalid].
  • A fork is where your program says 'do both of these at the same time'.
  • The join is where you say 'wait until both are done before moving on.'
  • Activity diagrams are great for modeling business logic, use case flows, or any algorithm before you write the code. Think of it as pseudocode you can draw.

Activity Diagrams

  • Model workflow or process flow of a system.
  • Notation:
    • Start (solid circle) required
    • End (circle with solid circle inside)
    • Activities (rounded rectangles)
    • Flow between activities (arrows)
    • Conditions (diamonds)
    • Forks (horizontal bars, 1 in many out)
    • Joins (horizontal bars, many in 1 out)
  • This activity diagram models the Withdraw Cash use case.

Activity Diagrams

The Withdraw Cash activity diagram flows top to bottom. The diagram begins with an initial pseudostate, represented as a solid filled circle, at the top center. Flow moves down to an activity labeled Insert Card, then continues down to Input PIN. From Input PIN, flow moves down to a decision node labeled "card accepted?" If the answer is yes, flow moves right to Select Action, then down to Withdraw Cash, then down to an abbreviated activity labeled "…and so on… (verify funds, dispense, receipt, etc.)," which represents the remainder of the withdrawal sub-process. That path then leads down to a wide horizontal join bar near the bottom of the diagram. If the card is not accepted, flow moves left from the "card accepted?" decision to a second decision node labeled "tried 3 times?" If the answer is yes, flow moves down to a thick horizontal fork bar, which splits into two concurrent parallel flows. The left branch leads to Terminate Transaction and the right branch leads to Notify Bank. Both branches flow down and converge at the same wide horizontal join bar that also receives the successful withdrawal path. If the answer to "tried 3 times?" is no, flow curves back up and returns to Input PIN, allowing the customer to try again. All paths — the two parallel branches from the failed authentication route and the completion of the successful withdrawal route — synchronize at the join bar before flow continues down to Eject Card. From there, flow moves down to the final pseudostate, represented as a solid filled circle inside an outer ring, which marks the end of the activity.

  • Tell students they will see five short ATM scenarios. For each one they must do two things: name the relationship type (include, extend, or generalization) and write one sentence explaining why.
  • 1 is extend. The base use case Withdraw Cash completes successfully without the SMS notification. The behavior is conditional — it only fires when the customer has opted in — and the base use case has no knowledge of it.
  • 2 is extend. Authenticate completes successfully in the normal flow without card retention. The fraud flag is a specific condition that triggers the extending behavior, and the base use case is unaware of it.
  • 3 is generalization. International Withdrawal is not a conditional addition — it is a specialized version of Withdraw Cash that inherits the complete base behavior and replaces or augments specific steps. It is always an international withdrawal when it occurs, not sometimes.
  • 4 is generalization at the actor level. Corporate Account Holder is-a Customer. It inherits all customer capabilities and adds specific ones. The arrow points from the specialized actor toward the general actor, the same direction as a class hierarchy in Java.
  • 5 is include. The account freeze check is mandatory, always occurs, and is shared across multiple use cases. There is no condition under which Withdraw Cash or Deposit Funds proceeds without it.

Candidate Object Identification

  • Techniques to find candidate classes:
    • Noun Extraction
    • BCE Taxonomy
  • Once we have identified the nouns, we can use EAR to determine which should become classes.
  • First, we determine if it has independent identity in the system (e.g. not an actor or the system itself).
  • Then, we consider if it has at least one persistent attribute.
  • Finally, we consider if it has relationships to other entities.
  • If it has each of these qualities, we should consider making it a class.

Turning Candidate Objects into Classes

  • For each candidate, evaluate it using the E.A.R. framework:
    • Entity: What "thing" is it? Does it contain component parts?
    • Attributes: What attributes describe the entity? Note that while these become fields, not all fields (like flags or counters) are attributes.
    • Relationships: What other entities does this entity need or use?
  • Customer = Actor
  • ATM = System itself
  • Account = Entity (identity in system; attribues like balance, accountId; needs/uses other entities, like receipt)
  • Current balance = Attribute of account
  • Daily withdrawal limit = Attribute of account
  • Cash = No attributes
  • Receipt = Entity (identity in system, attributes like date, time; needs/uses other entities, like account)

Noun Extraction (5 minutes)

  • Work in pairs.
  • Extract the nouns from this requirement and classify them as an Entity (Object) or an Attribute.
  • A customer interacts with the ATM to make a withdrawal from their account. The account checks the current balance and a daily withdrawal limit. The cash is then dispensed and a receipt is printed.
  • EAR gets us most of the way there, but can only see things that store data.
  • The objects responsible for actually running a withdrawal — checking the balance, calling the bank, telling the dispenser to release cash — those don't store anything. They just orchestrate.
  • EAR will never surface them because they fail the attributes test.
  • So we need one more step that answers a different question: not 'what data does this class hold,' but 'what role does this class play in the system.'
  • For large systems, it can be useful to categorize similar things.
  • Problem: If we put UI, business logic, and data in one class, our system becomes a fragile "God Class."
  • Solution (BCE): Categorize our classes into three types.

The BCE Taxonomy

  • For software systems, we can categorize our classes:
    • Boundary: Interfaces with actors
    • Control: Implements system logic and coordinates tasks
    • Entity: Stateful objects containing system information
  • The Golden Rule: Boundaries never talk directly to Entities. All communication goes through Control objects.

Boundary Objects

  • Inside our system, but interface with elements outside the system.
  • They are a "portal" or "gateway" between outside and inside.
  • Accepting a card requires writing specific command bit patterns to device driver memory locations (turn on the rollers to accept a card).
  • Initiating that command requires a second write to a separate memory location (to initiate that command request).
  • This is hardware-protocol logic; volatile, vendor-specific, and completely irrelevant to your business logic.
  • The CardReader object is inside our system, but up against the boundary acting as a conduit to the outside world device.

Boundary Objects: CardReader Example

  • The Problem: Hardware devices speak a low-level language your application should never have to know.
  • The Solution: Wrap it in a Boundary Object.

					// The rest of the system never sees device registers or bit patterns.
					// It only knows one thing:
					cardReader.acceptCard();
  • Control objects manage behavior; they coordinate the other objects so neither entity nor boundary objects have to.
  • Where Entity objects are the nouns, Control objects are the verbs (withdraw, authenticate, deposit).

Control Objects

  • Orchestrate the flow and manage behavior.
  • Coordinate the other objects so neither entity nor boundary objects have to interact directly.
  • One main controller initializes everything; separate controllers per major use case.
  • The AtmController object instantiates boundary objects.
  • Its main menu would create a WithdrawController object when the user indicates they want to make a withdrawal.
  • The WithdrawController object manages the flow of the transation.
  • When the transation is complete, the WithdrawController object is done an not re-used.
  • A subsequent withdrawal will get a new WithdrawController object, you cannot accidentally carry a balance from one withdrawal into the next.

Control Objects: ATM Example

  • Application Scope vs. Transaction Scope:
    • AtmController: Handles system startup, main menus, and hardware initialization; lives until the ATM shuts down.
    • WithdrawController: Manages a single withdrawal flow; created dynamically and destroyed when transaction finishes.
  • Architectural Value: Each transaction gets its own controller, state, and lifecycle, ensuring no shared mutable state between transactions.
  • Entity objects are the nouns we extracted that passed the EAR test.

Entity Objects

  • Represent information, data, and state needed by the system; not boundary objects.
  • They are not just data containers; they provide methods that act on their own data.
  • When your ATM transaction is completed, you get a receipt printed out.
  • The Receipt is not a boundary object. It never touches anything external.
  • As you progress through the transation, we build up this entity object.
  • Its entire job is to accumulate and hold the meaningful data that represents a completed transaction.
  • That’s the hallmark of an entity object: it models something real and stateful within your business domain.
  • The Receipt entity carries the what.
  • The Printer and TransactionLog boundary objects handle the how of interacting with the outside world.
  • Neither needs to know anything about the other’s domain.
  • Also: The Entity object is simpler to grasp: it holds system information. But don't confuse it with a plain data structure. Your Account object doesn't just store a balance — it has a debit() method, a credit() method, validation logic. It's an object in the full OO sense.

Entity Objects: Receipt Example

  • The printer is a boundary object, but the receipt is likely an entity object.

					// State accumulates as the transaction progresses

  • Useful for depicting an isolated part of a complex system.
  • Often used to visualize the current state of complex data structures.

Sequence Diagrams

  • Model interactions between objects over time.
  • Can be high-level (system overview) or low-level (method calls).
  • Can include conditionals and loops.
  • Notation:
    • Objects (boxes across top)
    • Lifelines (dashed vertical lines)
    • Messages (horizontal arrows)
    • Activation bars (thin rectangles)
  • The sequence diagram further refines the behavior associated with a use case.
  • Messages and returns
    • Solid arrow is method call / message sent
    • Dashed arrow is return value
  • Conditionals and loops
    • Wrapped in a fragment box with alt (if/else), opt (optional, single if), loop (repeating interaction)
  • To do a sequence diagram we need to have identified the use case, hopefully have considered an activity diagram for it, and begun our class diagram.
  • The "purpose" of the sequence diagram is to map high-level, domain-specific activities (use case's activity diagram) into the classes of our class structure.
  • So, this model affects ONE use case and MANY/ALL classes (just the ones we actually need, but there's no limit).

  • Notice that we are identifying some class/object methods that will become part of our solution! We can continue to refine our class diagram by adding this new information.

Sequence Diagrams (25 minutes)

  • Organize into small groups (3-4).
  • Begin work on the Sequence Diagram Assignment in the Canvas course.
  • The activity diagram is a high-level, flow of activities perspective of a use-case functionality.
  • The sequence diagram is a temporal perspective showing interactions of any objects (classes) used to achieve a single use case.
  • A state diagram is another approach for modeling the dynamic perspective.
  • The state diagram, in a way, is the inverse of the sequence diagram. It has no temporal emphasis and shows how a single object (class) changes state in response to requests that could be from many use cases.
  • A "movie" vs. the object diagram's "photograph"
  • Every state is a moment where the object is doing something or waiting
  • Rule: If it takes time → it's a state
  • The end state is optional because some objects never truly terminate (e.g. a running server)
  • Transitions are instantaneous, and usually occur based on specific conditions/events

State Diagrams

  • Models behavior of a single object.
  • Models one part of the system.
  • Similar to state machine diagrams (from Theory).
  • Notation:
    • Start (solid circle) required
    • End (circle with solid circle inside) optional
    • States (rounded rectangles)
    • Transitions (arrows between states)
  • Inside each state are 3 hooks
  • Entry is like walking through a door (fires once)
  • Do is everything you do in the room
  • Exit fires the moment you leave

Inside a State

  • Name (required, descriptive)
  • Attributes (values associated with a state)
  • Activities (actions the state performs)
    • Entry: Fires when state is entered
    • Do: Runs while inside the state
    • Exit: Fires when state is left
