The Strategy Design Pattern

Strategy defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it. — Gang of Four, Design Patterns (1994)
  • Encapsulate what varies
  • Favor composition over inheritance
  • Program to interfaces (abstractions), not implementations
  • This is the classic OOP setup you've seen before.
  • We have a Duck superclass that handles the shared behavior.
  • Subclasses inherit everything and just override display() to look different. Elegant. Works great. The team is happy.
  • Notice: fly() is in the superclass. That means every duck — every single concrete Duck subclass — inherits the exact same flying behavior.
  • At the time this code was written, that seemed fine. All ducks fly, right?

  • Someone on another team, quite reasonably, adds a RubberDuck class. It extends Duck. It inherits fly(). And now rubber ducks are zooming across the screen.
  • No bug in any single method. No compiler warning, only discovered at runtime. This is a design defect — a problem baked into the structure of the code.
  • In production software, this exact kind of inheritance-driven surprise causes real failures.
  • Think about what happens in a banking system when a new Account subclass inherits a chargeOverdraftFee() method it should never execute.
  • The lesson: We didn't anticipate this use of our code. Our design "broke" because inheritance tied all subclasses to one implementation of fly().

  • But...
    • We can’t anticipate every possible thing

      • YAGNI: You Aren’t Gonna Need It
  • We hadn’t thought about this contingency
  • It’s okay though: We “embrace change”

We Embrace Change

  • RubberDuck subclass wants to fly() in a different way
  • The “fix” must minimize changes needed as other new Duck subclasses want to fly() in different ways
  • What are the design options?
  • Three options, all inadequate. We will walk through each one.
  • Option 1 is an empty override. Seems harmless, but imagine you have 40 duck subclasses over two years.
  • Someone adds DecoyDuck. Should it fly? Probably not. Do they remember to override fly() with an empty body? Maybe. One missed override and production is broken.
  • And this approach also violates what I'd call the contract of the superclass — if Duck declares fly(), callers expect it to do something.

Option 1: Override fly() with an empty method

						
							class RubberDuck extends Duck {
								void fly() { /* do nothing */ }  // "degenerate" method
							}
  • Empty methods are a code smell; they make a promise they don't keep.
  • Every new non-flying subclass must remember to override. You will miss one.
  • Java 8 default interface methods make this option even more tempting.
  • But if 30 of your 40 duck subclasses fly the normal way, and you change the normal flying logic, you just created 30 files to touch.
  • Duplication is always a maintenance liability.

Option 2: Pull fly() into a Flyable interface

						
							interface Flyable { void fly(); }
							class MallardDuck extends Duck implements Flyable {
								public void fly() { /* regular flying */ }
							}
  • Every flying subclass must implement fly() itself; duplicate code everywhere.
  • Java 8 default methods can reduce this, but only for one shared implementation. A second flying style brings duplication back.
  • Option 3 is the big if-else. Duck.java becomes a graveyard for every flying implementation anyone ever invents.
  • The class grows without limit. Every change requires touching it. This is the opposite of scalable design (open-closed principle states that software entities should be open for extension, but closed for modification).
  • None of these work. Which tells us: the problem is deeper than the solutions we've tried.
  • The root issue is that fly() — a behavior that varies — is trapped inside the class hierarchy.
  • Let's look at the design principle that names this problem and its fix.

Option 3: Parameter dispatch in the superclass

						
							class Duck {
								void fly(int how) {
									if (how == 1) { /* regular */ }
									else if (how == 2) { /* none */ }
									else if (how == 3) { /* fast */ }
								}
							}
  • Duck.java changes every time any new flying style is needed. Violates OCP.
  • Every subclass still overrides just to pass the parameter. Nothing is solved.
  • This is the foundational insight: find what varies, pull it out, give it its own home.
  • For us: fly() implementations are the thing that varies. So we're going to extract them.
  • We define a FlyBehavior interface.
  • We create separate classes — FlyWithWings, NoFly, FlySlow, FlyRocketPowered — each implementing that interface in its own way.
  • Now Duck doesn't own the flying algorithm at all. It just references something that knows how to fly.

Design Principle 1: Encapsulate What Varies

Identify the aspects of your application that vary and separate them from what stays the same.
  • What stays the same: A Duck is a Duck. It quacks, swims, displays. That's stable.
  • What varies: How a duck flies. Multiple implementations needed, more will come.
  • The fix: Don't put varying behavior inside the class hierarchy. Encapsulate it separately.
