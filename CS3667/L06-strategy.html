The Strategy Design Pattern

Strategy defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it. — Gang of Four, Design Patterns (1994)
  • Encapsulate what varies
  • Favor composition over inheritance
  • Program to interfaces (abstractions), not implementations
  • This is the classic OOP setup you've seen before.
  • We have a Duck superclass that handles the shared behavior.
  • Subclasses inherit everything and just override display() to look different. Elegant. Works great. The team is happy.
  • Notice: fly() is in the superclass. That means every duck — every single concrete Duck subclass — inherits the exact same flying behavior.
  • At the time this code was written, that seemed fine. All ducks fly, right?

  • Someone on another team, quite reasonably, adds a RubberDuck class. It extends Duck. It inherits fly(). And now rubber ducks are zooming across the screen.
  • No bug in any single method. No compiler warning, only discovered at runtime. This is a design defect — a problem baked into the structure of the code.
  • In production software, this exact kind of inheritance-driven surprise causes real failures.
  • Think about what happens in a banking system when a new Account subclass inherits a chargeOverdraftFee() method it should never execute.
  • The lesson: We didn't anticipate this use of our code. Our design "broke" because inheritance tied all subclasses to one implementation of fly().

  • We should try to make our designs “goof proof”
  • But...
    • We can’t anticipate every possible thing
    • We shouldn’t add unneeded complexity
      • YAGNI: You Aren’t Gonna Need It
  • We hadn’t thought about this contingency
  • It’s okay though: We “embrace change”

We Embrace Change

  • RubberDuck subclass wants to fly() in a different way
  • The “fix” must minimize changes needed as other new Duck subclasses want to fly() in different ways
  • What are the design options?
  • Three options, all inadequate. We will walk through each one.
  • Option 1 is an empty override. Seems harmless, but imagine you have 40 duck subclasses over two years.
  • Someone adds DecoyDuck. Should it fly? Probably not. Do they remember to override fly() with an empty body? Maybe. One missed override and production is broken.
  • And this approach also violates what I'd call the contract of the superclass — if Duck declares fly(), callers expect it to do something.

Option 1: Override fly() with an empty method

						
							class RubberDuck extends Duck {
								void fly() { /* do nothing */ }  // "degenerate" method
							}
  • Empty methods are a code smell; they make a promise they don't keep.
  • Every new non-flying subclass must remember to override. You will miss one.
  • Java 8 default interface methods make this option even more tempting.
  • But if 30 of your 40 duck subclasses fly the normal way, and you change the normal flying logic, you just created 30 files to touch.
  • Duplication is always a maintenance liability.

Option 2: Pull fly() into a Flyable interface

						
							interface Flyable { void fly(); }
							class MallardDuck extends Duck implements Flyable {
								public void fly() { /* regular flying */ }
							}
  • Every flying subclass must implement fly() itself; duplicate code everywhere.
  • Java 8 default methods can reduce this, but only for one shared implementation. A second flying style brings duplication back.
  • Option 3 is the big if-else. Duck.java becomes a graveyard for every flying implementation anyone ever invents.
  • The class grows without limit. Every change requires touching it. This is the opposite of scalable design (open-closed principle states that software entities should be open for extension, but closed for modification).
  • None of these work. Which tells us: the problem is deeper than the solutions we've tried.
  • The root issue is that fly() — a behavior that varies — is trapped inside the class hierarchy.
  • Let's look at the design principle that names this problem and its fix.

Option 3: Parameter dispatch in the superclass

						
							class Duck {
								void fly(int how) {
									if (how == 1) { /* regular */ }
									else if (how == 2) { /* none */ }
									else if (how == 3) { /* fast */ }
								}
							}
  • Duck.java changes every time any new flying style is needed. Violates OCP.
  • Every subclass still overrides just to pass the parameter. Nothing is solved.
  • This is the foundational insight: find what varies, pull it out, give it its own home.
  • For us: fly() implementations are the thing that varies. So we're going to extract them.
  • We define a FlyBehavior interface.
  • We create separate classes — FlyWithWings, NoFly, FlySlow, FlyRocketPowered — each implementing that interface in its own way.
  • Now Duck doesn't own the flying algorithm at all. It just references something that knows how to fly.

Design Principle 1: Encapsulate What Varies

Identify the aspects of your application that vary and separate them from what stays the same.
  • What stays the same: A Duck is a Duck. It quacks, swims, displays. That's stable.
  • What varies: How a duck flies. Multiple implementations needed, more will come.
  • The fix: Don't put varying behavior inside the class hierarchy. Encapsulate it separately.

Design Principle 1: Encapsulate What Varies

UML class diagram showing the FlyBehavior interface and its two concrete implementations. At the top, an interface named FlyBehavior (displayed in italics with the stereotype label «interface») declares one method: fly(). Two concrete classes implement this interface via dashed arrows with open triangle arrowheads pointing up to FlyBehavior: FlyWithWings (on the left), which implements fly() with the comment implements duck flying; and FlyNoWay (on the right), which implements fly() with the comment do nothing - cant fly!
  • We are un-doing the inheritance of fly().
  • Instead of Duck being a flyer, Duck has a flying behavior. That's composition.

Design Principle 2: Favor Composition Over Inheritance

HAS-A can be better than IS-A.
  • Inheritance → IS-A relationship → tight coupling, fixed at compile time
  • Composition → HAS-A relationship → loose coupling, can change at runtime
  • Because myWayToFly is a field — a reference — its value can be assigned at construction time and even changed later at runtime.
  • The class hierarchy is fixed when the code compiles. A composition field is flexible the entire time the program runs.
  • This is a hard shift if you've been writing OOP code for a while. The instinct is always "add a subclass."
  • The Strategy pattern trains you out of that instinct for behaviors that vary.

Design Principle 2: Favor Composition Over Inheritance

  • Duck doesn't know how flying works. It delegates to whatever myWayToFly is holding.
						
							// Duck is no longer implementing fly(), it HAS a flying behavior
							class Duck {
								private FlyBehavior myWayToFly;  // ← composition

								public void fly() {
									myWayToFly.fly();  // ← delegation
								}
							}
  • This one sounds obvious, but it has a common misconception attached to it.
  • "Program to an interface" does not specifically mean "use the Java interface keyword."
  • Head First is explicit about this: what it means is "program to a supertype."
  • If FlyBehavior were an abstract class instead of an interface, this principle would be just as satisfied.
  • The point is the declared type of the field. If that field is declared as FlyBehavior, the Duck has no dependency on FlyWithWings or NoFly specifically.
  • It only knows the contract. That's what makes the whole thing swappable.

Design Principle 3: Program to Interfaces, Not Implementations

  • Duck is no longer calling a concrete fly(), it's using the FlyBehavior abstraction.
  • Declaring the field type as FlyBehavior (not FlyWithWings) means any concrete implementation can be swapped in, now or in the future.
  • The point is the declared type of the field. If that field is declared as FlyBehavior, the Duck has no dependency on FlyWithWings or NoFly specifically.
  • It only knows the contract. That's what makes the whole thing swappable.

Design Principle 3: Program to Interfaces, Not Implementations

						
							class Duck {
								protected FlyBehavior myWayToFly;  // declared as the INTERFACE type

								public void fly() {
									myWayToFly.fly();  // Duck has no idea which concrete class is in here
								}
							}
  • We've earned the definition now. Let's map it back to what we just built.
  • "Family of algorithms" — that's our FlyBehavior implementations.
  • "Encapsulates each one" — each lives in its own class.
  • "Makes them interchangeable" — they all satisfy the same interface, so the Context doesn't care which one is loaded.
  • "Algorithm varies independently from clients" — Duck has zero lines to change when someone adds FlyRocketPowered.
  • When you name a pattern in a design conversation, you're communicating a whole package of decisions at once.
  • "We use Strategy for the payment processor" tells your teammates: there's a Context, a family of interchangeable algorithms, runtime swapping is supported, and the Context is closed for modification.
  • Four architectural facts in four words. That's the value of learning the vocabulary, not just the structure.

The Strategy Pattern Defined

Definition Term Our Design
family of algorithms FlyWithWings, NoFly, FlySlow, FlyRocketPowered
encapsulates each one Each in its own class implementing FlyBehavior
makes them interchangeable All implement the same FlyBehavior interface
algorithm varies independently from clients Duck changes zero lines when a new flying style is added
  • Here's the fully assembled design.
  • Notice what Duck's fly() method contains: exactly one line — myWayToFly.fly().
  • It doesn't know how flying works. It delegates to whatever concrete behavior is stored in that field. That's delegation.

Putting It All Together

						
							class Duck {
								protected FlyBehavior myWayToFly;  // the strategy delegate

								public void fly() {
									myWayToFly.fly();                // delegation
								}

								public void setFlyBehavior(FlyBehavior newFB) {
									myWayToFly = newFB;              // runtime swap
								}
							}
  • The constructors of the concrete Duck subclasses assign which behavior they want at creation time.
  • RubberDuck gets NoFly. MallardDuck gets FlyWithWings.
  • And the setFlyBehavior() setter means that assignment can be changed later — while the Duck object is still alive and in use.
  • That's the runtime flexibility composition gives us that inheritance never could.

Putting It All Together

						
							class RubberDuck extends Duck {
								public RubberDuck() {
									myWayToFly = new NoFly();        // assigned at construction
								}
							}

							class MallardDuck extends Duck {
								public MallardDuck() {
									myWayToFly = new FlyWithWings(); // assigned at construction
								}
							}
  • fly() is now decoupled from Duck. Duck is loosely coupled with its FlyBehaviors.
  • One note from the textbook worth calling out explicitly: Head First names the Context method performFly() rather than fly().
  • That's deliberate — performFly() is Duck's public API; fly() is the Strategy contract on FlyBehavior.
  • Two layers, two names, so you can always tell which object you're looking at.
  • In StreamNet, our Context method and Strategy method will have matching names but different signatures, which serves the same purpose.

Putting It All Together

  • George is a MallardDuck. His myWayToFly field holds a FlyWithWings object. He flies normally.

George!

  • Meet George, a MallardDuck who lives at the duck pond.
						
							Duck george = new MallardDuck();
							george.fly();   // delegates to FlyWithWings → "I'm flying!"
  • George gets hurt. In an inheritance-only world, what are your options?
  • Override fly() to do nothing? That's Option 1 — we already know that's bad.
  • Create an InjuredMallardDuck subclass? Now your class hierarchy is modeling a health condition. That's absurd.
  • With Strategy: one line. george.setFlyBehavior(new NoFly()).
  • George is the same Java object. The Duck george reference hasn't changed.
  • What changed is the object that myWayToFly points to. The behavior is swapped. That's the payoff.
  • One thing to notice: in MallardDuck's constructor, we write new FlyWithWings(). This is instantiating a concrete class.
  • A sharp student might ask — doesn't that violate "program to abstractions"?
  • It does, a little. We've pushed that concrete coupling out to the constructor, and further out to Main.
  • Head First acknowledges this tension directly: "Good catch — that's exactly what we're doing... for now."
  • Later in the book, the Factory pattern is covered and shows how to solve this properly.
  • For now, understand the tradeoff: concrete instantiation confined to one place is far better than scattered through every method that needs a behavior.

George!

  • Then George injures his wing. He can't fly anymore.
  • With inheritance, you'd need a new subclass InjuredMallardDuck. Or an empty override. Neither is good.
  • With Strategy, just swap the delegate.
  • George is the same object. His class didn't change. His behavior did.
						
							george.setFlyBehavior(new NoFly());
							george.fly();   // delegates to NoFly → "I can't fly."
  • Three roles: Context, Strategy Interface, Concrete Strategies.
  • The Context HAS-A strategy reference. It delegates behavioral calls to that reference.
  • The Concrete Strategies IMPLEMENT the interface, each providing a different algorithm.
  • The Context IS-A... well, in our case Duck has subclasses, but the key relationship for the pattern is the HAS-A.
  • HFDP's Big Picture diagram shows something worth noting: the same Context can hold multiple independent strategy delegates (see UML diagram a few slides ago).
  • Duck has both flyBehavior and quackBehavior. Two completely independent variation axes, each encapsulated separately, each swappable independently.
  • In StreamNet, your VideoClip will carry one strategy delegate for rendering.
  • You could — in a future sprint — add a second delegate for encoding. Same Context, two HAS-A relationships, two strategy families. The pattern scales.

  • VideoClip is the Context.
  • VideoRenderBehavior is the Strategy interface.
  • SdrRender, HdrRender, and DolbyVisionRender are the Concrete Strategies.
