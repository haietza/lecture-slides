Git and GitHub

  • Before we write enterprise code, we need to know how to manage it.
  • Manual copying, timestamped files were used in the early days.
  • Then came centralized systems, but if the server went down, work stopped.
  • Historically, version control stored 'deltas' — just the changes between files.
  • Git is distributed, your computer holds the full history.
  • Git revolutionized version control by taking a snapshot of your entire project at a given point in time.

Evolution of Version Control

  • Local Systems: Manual copying, backup folders (timestamped). Full copies of files.
  • Centralized Systems (CVS, Subversion): Single server maintains deltas. Single point of failure.
  • Distributed Systems (Git, Mercurial): Peer-to-peer. Each peer "fully mirrors" the repository.
  • Under the hood, Git bundles your code with meta-data into a 'blob' and assigns it a SHA-1 hash.
  • This hash ensures integrity; if a single bit changes, the hash changes.

Git's Secret Sauce: Snapshots

  • Git uses project “snapshots” not file deltas/diffs.
  • Everything is check-summed using a SHA-1 hash.
  • The SHA-1 hash (40 hex characters) is a unique identifier “key” in the database.
  • Any content deviation (accidental or intentional) is noticeable.
Git's Secret Sauce: The Power of Snapshots. Snapshots Over Deltas. Git captures the state of the entire project rather than just tracking file differences. The Data 'Blob'. Project code is bundled with metadata into a single unit known as a blob. The 40-Character Unique Key. Every snapshot is checksummed into a 40-hex character SHA-1 hash. Built-in Integrity. If even a single bit changes, the hash deviates, making any corruption noticeable. Content-Addressable Database. The SHA-1 hash acts as the unique database key for retrieving specific snapshots. Permanent Storage. These snapshots are stored permanently in the .git directory after every commit.

The Three Local States of Git

  • Working Directory: Where you edit files.
  • Staging Area (Index): Where you prepare files for commit.
  • Repository (.git directory): Where Git permanently stores the snapshots.
The 3 Stages of Git. Master the local lifecycle of your code by moving files through Git's three core environments. Working Directory: The Edit Zone. This is the local folder wher eyou actively modify and create your files. Staging Area: The Prep Zone. Also known as the Index, this is where you bundle specific changes before committing. Repository: The Permanent Storage. The .git directory where Git permanently stores your projec snapshots and metadata.
  • When you edit a Java file, it's just in your Working Directory.
  • Git knows it's modified, but it won't track the changes until you 'stage' them with git add.
  • Staging allows you to group logical changes together.
  • Finally, git commit takes everything on the stage and permanently stores it in the .git folder as a snapshot.

The Basic Git Workflow

  • Edit files in the working directory.
  • git add [filename(s)]: Puts files in the staging area.
  • git commit -m "[commit message]": Puts files that are in the staging area into the repository.

The Commit Cycle Activity (15 mins)

  • Create User.java with a private fields for firstName and lastName and getter and setter methods.
  • Run git status to see it untracked.
  • Run git add User.java, then git status to see it staged.
  • Run git commit -m "Add User class".
  • Add a toString() method, stage, and commit with a clear message. Use git log to review the history.
  • In many older VCS tools, branching meant copying the entire project folder; it was slow and expensive.
  • In Git, a branch is just a 40-character file pointing to a specific SHA-1 commit hash. It's nearly instantaneous.
  • Think of branches as bookmarks; when you create a branch, you just create a new bookmark at the current commit.
  • When you run git checkout [branchname], Git moves the HEAD pointer to that branch and updates your Working Directory to match that snapshot.

Branches are Commit Chains

  • Branches are simply lightweight, movable pointers to a commit.
  • The default branch is now commonly called main.
  • Creating a branch: git checkout -b [branch-name] creates and checks out the branch.
  • HEAD is a special pointer that tells Git which branch you are currently on.

Branching Context Switch Activity (15 mins)

  • In the existing repo, create and checkout a new branch: git checkout -b feature-auth.
  • Add an Auth.java file. Commit it.
  • Run git checkout main. Observe that Auth.java disappears from the file explorer in VS Code!
  • Checkout feature-auth again to see it reappear.
  • Merging brings isolated work back together.
  • If main hasn't changed since you branched off, Git just slides the pointer forward; a fast-forward.
  • But if someone else merged changes into main while you were working, Git performs a two-way merge, creating a new merge commit.

Types of Merges

  • Fast-forward merge: The "commit path" from the merging branch intersects the tip of the source branch. Git simply moves the pointer forward.
  • Two-way merge (Recursive): Changes have occurred on both branches. Git creates a new commit object with 2 parents.
  • If you both edited the same line of code, Git throws its hands up. This is a merge conflict.

Merge Conflicts

  • Occurs when changes conflict (e.g., same line edited in both branches).
  • Git pauses the merge. You must manually resolve conflicts in files marked by Git.
  • Use VS Code's merge conflict editor to Accept Current, Accept Incoming, or Accept Both.

  • So far, our snapshots have lived exclusively on our course VM.
  • To collaborate, we need a remote server like GitHub.
  • 'origin' is just the standard alias for the URL of your remote repository.
  • When we push, we are sending our commit chain up to GitHub.
  • When we clone or fetch, we are downloading the chain.

Working with Remotes

  • git clone [url]: Creates a local repository of an already existing remote repository.
  • git remote add origin [url]: Connects a local repo to a remote.
  • git push -u origin [branch]: Pushes your local branch to the remote.
  • git fetch: Pulls down remote data, but doesn't merge it.

The First Push Activity (15 mins)

  • Create an empty repository on GitHub.
  • In your terminal, add the remote: git remote add origin [your-url].
  • Push the code: git push -u origin main.
  • Verify the code appears on the GitHub website.
  • In professional software engineering, you rarely push directly to main.
  • You push a feature branch and open a Pull Request.
  • A PR is a request for your peers to review your code before it merges into the production branch.
  • This is where automated tests run and code reviews happen.

The Pull Request Workflow

  • Clone (one-time only).
  • Create/checkout local branch for a change request.
  • Work and commit locally.
  • Push the branch to GitHub.
  • On GitHub, generate a Pull Request (PR).
  • Review, approve, and merge on GitHub.

Collaborative PRs Activity (15 mins)

  • Work in pairs.
  • Add your partner as a Collaborator on your GitHub repo.
  • Partner clones the repo, creates a branch feature-logger, adds a System.out.println to a method, commits, and pushes the branch.
  • Partner opens a Pull Request on GitHub.
  • You review the PR on GitHub, leave a comment, and click "Merge pull request".
  • Finally, pull the merged changes locally: git checkout main, git fetch origin, git merge origin/main.
  • Git is forgiving locally, but unforgiving once you share your history.
  • If you accidentally stage a file you didn't mean to, git restore --staged brings it back to the working directory.
  • If you realize your last commit message was terrible, git commit --amend lets you fix it.
  • But remember: never amend or alter commits that your teammates have already pulled.

Fixing Mistakes

  • Discard working directory changes: git restore [filename] (Removes uncommitted changes).
  • Unstage a file: git restore --staged [filename].
  • Modify last commit: git commit --amend (Use to fix typos in the last commit message or add missed files).
  • DO NOT rewrite history on branches that have already been pushed to a remote repository!

Fixing Mistakes Activity (15 mins)

  • Add a file Secrets.txt containing dummy passwords. Stage it (git add).
  • Realize the security flaw! Unstage it using git restore --staged Secrets.txt.
  • Create a .gitignore file and add Secrets.txt to it.
  • Run git status to verify Secrets.txt is no longer tracked. Commit the .gitignore file.
