Observer Design Pattern

The Observer Design Pattern

The Starting Problem:

  • Weather-O-Rama has a WeatherData object that receives live measurements: temperature, humidity, air pressure.
  • They want multiple displays (current conditions panel, statistics view, forecast) to update automatically whenever measurements change.
  • Weather-O-Rama provides the sensor devices, the weather station, and the WeatherData object.
  • We will need to implement the three different displays, and integrate the WeatherData object with thd display.

  • The textbook is blunt about it: we're coding to concrete implementations, and we have no way to add or remove display elements at runtime without altering this code.
  • Those are some of the problems the Observer pattern solves.

Violation 1

Coding to implementations, not interfaces

  • WeatherData references concrete display classes directly. It cannot be compiled without them.
  • Any structural change to a display class (a renamed method, a moved package) breaks WeatherData without touching it.

Violation 2

Open/Closed Principle broken

  • measurementsChanged() must be modified every time a display is added or removed.
  • The class is not closed for modification. Every new feature is an edit to working, tested code.

Violation 3

No runtime extensibility

  • There is no way to add or remove a display while the program is running.
  • All three displays are instantiated at construction time and fixed.
  • Turning off ForecastDisplay at 10 PM would require a null-check hack or a full recompile.

Violation 4

Failure to encapsulate what varies

  • The set of displays is exactly the thing that changes most often; product teams add and remove them constantly.
  • It is not encapsulated at all; it's hardwired into the method body.

Design Principle 4: Minimize Dependencies

Strive for loosely coupled designs between objects that interact.
  • WeatherData is tightly coupled to its displays.
  • It knows their class names, instantiates them directly, and calls them by name.
  • A loosely coupled design would mean WeatherData knows as little as possible about whoever is listening; ideally nothing beyond the fact that they respond to a single method call.

Design Principle 4: Minimize Dependencies

  • A loosely coupled Subject knows
    • That its observers have an update() method
    • That there are zero or more of them
  • A loosely coupled Subject does not know
    • Any observer's class name
    • What any observer does in update()
    • How many observers there are
    • Whether a given observer was added at startup or three sprints ago
  • Easy name to remember — we need to observe something, so we use the Observer pattern.
  • No tight coupling: Subject knows only that observers have an update() method, Subject and observer hierarchies are independently changeable and independently reusable
  • Multiple reactors without changing data-holder: A new Observer type can be added without touching Subject code
  • Reactors can register/de at runtime: Observers can come and go at runtime without the Subject caring

Observer Rundown: What We Need

The Observer pattern exists precisely for this situation:

  • Some object has data of interest to others
  • Others need to react when that data changes
  • No tight coupling between the data-holder and the reactors
  • Multiple reactors supported without changing the data-holder
  • Reactors can register and deregister at runtime
  • Before I show you the structure, I want you to feel the newspaper analogy. Think about how a print subscription works.
  • Key property: The publisher doesn't know anything about individual subscribers.
  • It just maintains a list and delivers to everyone on it.
  • Subscribers can join or leave at any time without the publisher caring.

The Newspaper Analogy

Pattern Role Newspaper World

Formal Definition

The Observer Pattern defines a one-to-many dependency between objects so that when one object changes state, all of its dependents are notified and updated automatically.
  • One-to-many: One Subject, potentially many Observers.
  • Dependency: Observers depend on the Subject for their data, but the Subject does not depend on any specific Observer type.
  • Automatically: Observers do not poll. The Subject pushes the notification.

Redesign

Without writing any code yet, how would you redesign measurementsChanged() so that WeatherData doesn't know the name of a single display class?

The Subject Lifecycle

  • Subject holds data of interest and maintains a collection of registered Observer objects
  • A new object calls registerObserver() → added to the collection
  • Subject data changes → Subject calls notifyObservers()
  • notifyObservers() loops over the collection and calls update() on each Observer
  • An object calls removeObserver() → removed from collection; no further notifications
  • The UML gives us two parallel hierarchies — Subject on the left, Observer on the right — connected only through interfaces.
  • As long as both sides honor the interface contracts, they work together. That's loose coupling delivering what it promised.

  • Look at notifyObservers(). It loops over a List<Observer>.
  • It does not call currentConditionsDisplay.update(), it calls o.update().
  • The concrete type behind that reference could be a CurrentConditionsDisplay, a StatisticsDisplay, a HeatIndexDisplay we haven't written yet, or a test spy we only use in unit tests.
  • The Subject has no idea and doesn't need to. That's polymorphism doing exactly its job.
  • Now look at measurementsChanged(). It went from three hardwired display calls to one call to notifyObservers().
  • WeatherData no longer names a single display class.

WeatherData + Observer

						
							import java.util.ArrayList;
							import java.util.List;

							public class WeatherData implements Subject {
								private final List observers = new ArrayList<>();
								private float temperature;
								private float humidity;
								private float pressure;

								@Override
								public void notifyObserver(Observer o) {
									observers.add(o);
								}

								@Override
								public void removeObserver(Observer o) {
									observers.remove(o);
								}

								@Override
								public void notifyObservers() {
									for (Observer o : observers) {
										o.update();  // Subject calls update(); Observer decides what to fetch
									}
								}

								public void measurementsChanged() {
									notifyObservers();  // replaces the three hardwired calls
								}

								// State accessors — available for pull model
								public float getTemperature() { return temperature; }
								public float getHumidity()    { return humidity;    }
								public float getPressure()    { return pressure;    }

								public void setMeasurements(float temperature, float humidity, float pressure) {
									this.temperature = temperature;
									this.humidity    = humidity;
									this.pressure    = pressure;
									measurementsChanged();
								}
							}
  • The SOLID connections are worth naming.
  • Think about adding a new display. You write a class, implement Observer, call weatherData.registerObserver(yourNewDisplay) from anywhere in the codebase — even at runtime. Zero existing files change.
  • Compare that to the broken version where you had to open measurementsChanged() every single time.
  • This is the Open/Closed Principle in practice: open for extension, closed for modification.
  • Both sides depend on abstractions. Neither imports the other's concrete class. That's Dependency Inversion.
  • These aren't incidental properties of the pattern; they're the direct result of the loose coupling principle applied consistently.

Push vs. Pull

  • The Observer pattern leaves one key implementation detail open: How does the Observer get the data it needs after update() fires?
    • Push Model: The Subject sends data as parameters of update().
    • Pull Model: The Subject sends only a notification signal. Observers pull what they need.

Push Model

						
							// Subject decides what to send
							public interface Observer {
								void update(float temperature, float humidity, float pressure);
							}

							public void notifyObservers() {
								for (Observer o : observers) {
									o.update(temperature, humidity, pressure);
								}
							}

Push Model

  • Advantage: Observers don't need a reference back to the Subject.
  • Problem: The Subject sends the same data to all Observers. When WeatherData adds windSpeed:
    • Every Observer implementation must update its update() signature.
    • Every concrete class must add the parameter even if it never uses it.
    • That is a cascading edit across every Observer in the codebase.
  • Best When: All observers need the same small data set.

Pull Model

						
							// Observer decides what to fetch
							public interface Observer {
								void update();   // no data — just the signal
							}

							public void notifyObservers() {
								for (Observer o : observers) {
									o.update();
								}
							}

Pull Model

						
							// Observer pulls only what it needs
							public class StatisticsDisplay implements Observer {
								private final WeatherData subject;   // back-reference — the "subject" arrow on the UML

								@Override
								public void update() {
									float temp = subject.getTemperature();   // fetches only what it needs
									recordTemperature(temp);
								}
							}
  • The push/pull question is where pattern knowledge becomes engineering judgment.
  • Push feels simpler — you pass the data right in the update() call.
  • But changing fields in the Subject means you have to change every Observer class in the codebase, even the ones that never use those fields.
  • The pull model avoides that situation. The interface stays stable.
  • update() is a signal that something changed.
  • Each Observer calls the getters it cares about.
  • A change to the fields in the Subject only involves adding a getter. Only the Observers that need it will ever call it.
  • The cost is the back reference to the Subject (so Observer can call those getters).
  • A mild increase in coupling at the concrete level in exchange for a stable interface contract.
  • That trade is almost always worth it.

Pull Model

  • Advantage: When WeatherData adds windSpeed, only the Observers that care call getWindSpeed().
    • The Observer interface never changes. No cascading edits.
  • Cost: Each Observer must hold a reference back to the Subject.
  • Best When: Observers vary in what they need.

Java's Built-In Observer Support

java.util.Observable (class) and java.util.Observer (interface) are available Java 1.0 through Java 8, deprecated in Java 9.
  • The deprecation of java.util.Observable is a clean lesson in why we design to interfaces — and it directly reinforces the loose coupling principle.
  • The designers of Java made Observable a class.
  • That single decision meant any Subject had to use its one inheritance slot to extend it.
  • If your domain object already extended something — which is common — you were out of options.
  • The lesson generalizes: when you're designing a base abstraction, prefer interfaces over classes wherever possible.
  • It's the same reasoning that makes our custom Subject and Observer interfaces better than what Java shipped.

Java's Built-In Observer Support

  • Observable was a class, not an interface.
  • Java permits only single inheritance of classes.
  • Any class wanting to be a Subject had to extend Observable, consuming its one inheritance slot.
  • If your domain model already needed to extend something else, you were stuck.
  • You will encounter java.util.Observable in legacy codebases. Know what it is and why it was replaced.
