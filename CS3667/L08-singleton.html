Singleton Design Pattern

  • Unlike Strategy or Observer, Singleton is deceptively simple to state but can be tricky to implement correctly.

The Singleton Design Pattern

Ensures a class has only one instance, and provides a global point of access to it.
  • The textbook's running example for this chapter is the Choc-O-Holic chocolate factory.
  • The chocolate boiler has three operations: fill(), boil(), and drain() — and each one has a guard condition, because doing them out of order is catastrophic.
  • You cannot fill an already-full boiler.
  • You cannot boil an empty one.
  • You cannot drain one that hasn't finished boiling.
  • What happens if two ChocolateBoiler objects get loose in the same application?
  • Two independently-tracked boilers means two independent sets of empty/boiled flags — but they both control the same physical hardware.
  • One object might think the boiler is empty and call fill() while the real boiler — being managed by the other object — is mid-boil.
  • This is the entire motivation for Singleton: when there's exactly one real-world thing being represented, your code should guarantee exactly one object represents it.
  • Now, how do we get instances of classes?
  • Through the constructor — new ChocolateBoiler().
  • So if we need to guarantee only one instance ever exists, what do we need to control? The constructor itself.

The ChocolateBoiler Class

						
							public class ChocolateBoiler {
								private boolean empty;
								private boolean boiled;

								public ChocolateBoiler() {
									empty = true;
									boiled = false;
								}
								// ... fill(), boil(), drain(), isEmpty(), isBoiled()
							}
  • Let's build this exactly the way the book does, one constraint at a time.
  • First constraint: make the constructor private.
  • Done — now literally nobody outside the class, not even your Main class, can write new ChocolateBoiler().
  • But that immediately creates a problem: if nobody can call the constructor, how does anybody ever get a ChocolateBoiler to work with?

Building the Classic Singleton

						
							// Step 1: lock the constructor
							public class ChocolateBoiler {
								private boolean empty;
								private boolean boiled;

								private ChocolateBoiler() {   // private! No outside class can call new ChocolateBoiler()
									empty = true;
									boiled = false;
								}
								// ... fill(), boil(), drain(), isEmpty(), isBoiled() unchanged
							}
  • The answer is the second constraint: a method inside the class can call a private constructor, because access modifiers are about what's visible from outside the class, not inside.
  • Line 14: So we write a public method, conventionally named getInstance(), that lives inside ChocolateBoiler and is the only code path that can ever call new ChocolateBoiler().
  • Why must getInstance() be static?
  • Because to call a normal instance method, you need an object reference to call it on — someBoiler.getInstance().
  • But we don't have a ChocolateBoiler object yet; that's the whole problem we're solving.
  • static lets us call it directly on the class: ChocolateBoiler.getInstance(), with zero objects required up front.
  • The if-check inside getInstance() is what makes this lazy. The object is only created when it is needed.
  • Line 4: And the field uniqueInstance — that has to be static too, for a related reason.
  • getInstance() is a static method, and static methods cannot reference instance-level fields.
  • The book makes an important comparison I want you to hold onto: this is similar to a global variable, but better, because we additionally get to choose when the object gets created.
  • We'll discuss lazy-versus-eager initialization soon.

Building the Classic Singleton

						
						// Step 2: but now NO class, including Main, can create one. We need an access point.
						// Methods INSIDE the class can call a private constructor.
						public class ChocolateBoiler {
							private static ChocolateBoiler uniqueInstance;   // static — class-level, not per-object

							private boolean empty;
							private boolean boiled;

							private ChocolateBoiler() {
								empty = true;
								boiled = false;
							}

							public static ChocolateBoiler getInstance() {     // static — callable without an instance
								if (uniqueInstance == null) {
									uniqueInstance = new ChocolateBoiler();
								}
								return uniqueInstance;
							}
							// ... fill(), boil(), drain(), isEmpty(), isBoiled() unchanged
						}

  • Despite implementing the classic Singleton correctly, ChocolateBoiler's fill() method somehow ran while a batch was already boiling.
  • How is that possible if getInstance() always returns the same object?
  • They'd just added multithreading optimizations to the boiler controller.
  • Thread 1 enters getInstance(). It evaluates uniqueInstance == null as true, since nothing has been constructed yet.
  • Right at that moment, the scheduler pauses Thread 1, hands control to Thread 2.
  • Thread 2 now runs the exact same check. uniqueInstance is still null, because Thread 1 never got far enough to assign anything.
  • So Thread 2 also gets true, constructs a ChocolateBoiler, assigns it, and returns it.
  • Now Thread 1 resumes, but it already evaluated its null-check back at the start. It goes straight to construction and creates a second ChocolateBoiler.
  • Two threads now hold two different boiler objects, each independently tracking its own empty/boiled flags for the same physical hardware.
  • The single-threaded version of this code implicitly assumes that nothing else can run between the null-check and the assignment.
  • That assumption is false the moment you have more than one thread.
  • And notice, from either thread's own point of view, nothing went wrong. The bug only exists in the interleaving between the two.
  • Any application server handling concurrent requests is exactly this situation, at scale, constantly. We need to fix it, and the book gives us three different ways to do it.

The Multithreading Problem

Thread 1 Thread 2
uniqueInstance == null → TRUE → [paused by scheduler here]
uniqueInstance == null → TRUE
uniqueInstance = new ChocolateBoiler() → <object1>
[resumes, already past the check]
uniqueInstance = new ChocolateBoiler() → <object2> ← VIOLATION: two boilers exist
  • Adding the synchronized keyword to the method signature guarantees mutual exclusion; only one thread can be executing inside getInstance() at any moment.
  • Go back to the race condition we just walked through: Thread One enters, the lock is acquired, and even if Thread One gets paused mid-method, it still holds the lock.
  • Thread Two tries to enter and simply cannot; it's blocked until Thread One finishes and releases the lock.
  • Synchronization is expensive (it can decrease performance by a factor of 100) and we only needed the protection during the very first call.
  • Every call after that, uniqueInstance is already set, the null-check will always be false, and yet we're still paying the synchronization tax on every single call forever.
  • That's the motivation for Fix 2 and Fix 3.

Fix 1: Synchronize getInstsance()

						
							public class ChocolateBoiler {
								private static ChocolateBoiler uniqueInstance;
								private boolean empty;
								private boolean boiled;

								private ChocolateBoiler() {
									empty = true;
									boiled = false;
								}

								// 'synchronized' forces every thread to wait its turn before entering this method.
								// No two threads may be inside getInstance() at the same time.
								public static synchronized ChocolateBoiler getInstance() {
									if (uniqueInstance == null) {
										uniqueInstance = new ChocolateBoiler();
									}
									return uniqueInstance;
								}
								// ... fill(), boil(), drain() unchanged
							}
  • Fix number two sidesteps the whole problem differently: don't wait for the first call at all.
  • Construct the object the moment the class is loaded, as part of the field declaration itself.
  • The JVM's class-loading mechanism is single-threaded and happens before any of your application's own threads start running, so this is automatically thread-safe with zero synchronization code written by you.
  • Line 14: getInstance() shrinks down to a one-line return. No null check needed, because the field is never null after class loading completes.
  • The trade-off: This only makes sense if your application is always going to need the Singleton anyway, or if constructing it is cheap.
  • If construction is expensive (say it opens a file, allocates a large buffer, or sets up an expensive resource) and your application might never actually need it, you've just spent that cost for nothing.
  • For our chocolate boiler, this is a completely reasonable choice; the book confirms the factory always uses exactly one boiler regardless.

Fix 2: Eager Initialization

						
							public class ChocolateBoiler {
								// Created immediately when the class loads, guaranteed thread-safe by the JVM itself
								private static ChocolateBoiler uniqueInstance = new ChocolateBoiler();

								private boolean empty;
								private boolean boiled;

								private ChocolateBoiler() {
									empty = true;
									boiled = false;
								}

								public static ChocolateBoiler getInstance() {
									return uniqueInstance;   // already exists — just hand it back
								}
								// ... fill(), boil(), drain() unchanged
							}
  • Fix number three: Only pay the synchronization cost during the narrow window where the object might not exist yet, and skip it entirely afterward.
  • Line 14: The outer if is the fast path. Once uniqueInstance is set, every future call short-circuits past the synchronized block entirely — zero lock overhead, after the first successful construction.
  • Line 16: The inner if, inside the synchronized block, is the double-check that givese.
  • If two threads both pass the outer check before either one has constructed the object, only one of them will actually get the lock first.
  • That thread does the inner check, sees null, and constructs.
  • The second thread then enters the block, does its own inner check, sees the object is no longer null, and skips construction entirely.
  • The volatile keyword is not optional here. Without it, the JVM and CPU are permitted to reorder operations and cache field reads per-thread.
  • volatile forces every read and write of that field to go through main memory, guaranteeing visibility of the fully-constructed object across all threads.
  • Double-checked locking is correct in Java 5 and later. Earlier JVMs had a flaw in the memory model around volatile that made this implementation unreliable.

Fix 3: Double-Checked Locking

						
							public class ChocolateBoiler {
								// volatile: ensures every thread sees the most up-to-date value, not a stale cached copy
								private volatile static ChocolateBoiler uniqueInstance;

								private boolean empty;
								private boolean boiled;

								private ChocolateBoiler() {
									empty = true;
									boiled = false;
								}

								public static ChocolateBoiler getInstance() {
									if (uniqueInstance == null) {  // Check 1 — no lock yet
										synchronized (ChocolateBoiler.class) {
											if (uniqueInstance == null) {. // Check 2 — inside the lock
												uniqueInstance = new ChocolateBoiler();
											}
										}
									}
									return uniqueInstance;
								}
								// ... fill(), boil(), drain() unchanged
							}
  • None of these fixes are "the best" in some absolute sense.
  • They each need to be evaluated against the specific object being protected.
  • It is an engineering judgement; the righr fix depends on two questions.
  • How expensive is construction?
  • How often is getInstance() called?
  • An object that's cheap to build and always needed → eager.
  • An object whose getInstance() is called rarely → synchronized is fine, the overhead barely matters.
  • An object that's expensive to build and called extremely frequently → double-checked locking earns its complexity.

Choosing a Fix

  • Synchronize getInstance(): No performance concerns with chocolate boiler; this fix would be a good choice.
  • Eager instantiation: We are always going to instantiate the chocolate boiler in our code; this fix would work well, but may be less obvious to a developer familiar with synchronize.
  • Double-checked locking: No performance concerns; this fix seems like overkill.
