Command Design Pattern

Home Automation Remote Control

You've been hired to design the API for a universal home-automation remote. It has seven programmable slots, on/off buttons for each, and one global undo button. Vendors will supply the actual devices (lights, hot tubs, garage doors, stereos) and you don't get to control what methods those classes expose.
  • These interfaces have almost nothing in common.
  • There's no shared activate()/deactivate() you can lean on.
  • And the spec says more vendor classes are coming later; you don't even get to see all of them now.

The Naive First Attempt

						
							public void onButtonWasPushed(int slot) {
								if (slot == 1) {
									light.on();
								} else if (slot == 2) {
									hottub.jetsOn();
								} else if (slot == 3) {
									garageDoor.up();
								}
								// ...and one more else-if for every slot, forever
							}
  • You've got seven slots, an unknown and growing list of vendor classes, and a due date.
  • The if/else version works. It compiles, it runs, the demo goes fine.
  • The problem shows up six months later when Vendor #8 ships a SecurityControl class with arm()/disarm(), and you have to reopen RemoteControl.java, add a branch, retest the whole method, and hope you didn't break anything while you were in there.
  • The real insight — and this is the one the pattern is built around — is this: the remote doesn't need to know what a button does.
  • It only needs to know that pressing a button triggers something.

Why The Naive Attempt Breaks

  • Every new vendor class means editing this method again.
  • The remote's own source code now depends on every vendor class that exists.
  • Separation of concerns failure: The remote should know how to interpret a button press; it should not need to know how a hot tub works.
  • What if every slot just held an object whose entire job was do the one thing it was configured to do, and the remote's only responsibility was calling that object's one method?
  • Then the remote's code never changes again, no matter how many vendors show up.
  • We're going to borrow a mental model from a diner to make it concrete, and then we're going to come back and actually build this remote.

The Command Design Pattern

Encapsulates a request as an object, thereby letting you parameterize other objects with different requests, queue or log requests, and support undoable operations.
  • Let's start with a real-world analogy: the Objectville Diner from the textbook.
  • The interaction between a customer, a waitress, and a cook has exactly the same decoupling shape we just described.
  • In our OO mindset, we look for the nouns as objects of classes.

The Order Object

  • The order has exactly one relevant method from the waitress's point of view: orderUp().
  • The order also holds a reference to whoever needs to do the work (the Cook).
  • The waitress never needs to know what is being cooked, or how. She only knows every order she's handed supports orderUp().

Command Pattern Roles

  • The Client decides what Command to create.
  • The Invoker asks for something to happen, without knowing how it happens.
  • The Command is a stand-in for the action, that can be handed around and triggered later.
  • The Receiver is the one who actually knows how to do the work.
  • The ConcreteCommand is the specific kind of Command.

The Command Interface

						
							public interface Command {
								public void execute();
							}
  • This is a specific Order (Command)
  • Line 4: It knows which Receiver (Light) it's bound to (passed in the constructor)
  • Line 9: And it knows what to tell it to do (turn on the light in the light instance variable).

A Concrete Command

						
							public class LightOnCommand implements Command {
								Light light;

								public LightOnCommand(Light light) {
									this.light = light;
								}

								public void execute() {
									light.on();
								}
							}
  • This is the Waitress. There is no Light anywhere in this class. It cannot see the vendor classes at all.
  • Line 2: We have one slot to hold our command, which controls one device.
  • Line 6: We have a method for setting the command the slot is going to control.
  • Line 10: We have a method that is called when the button is pressed; it just takes the current command bound to the slot and calls its execute() method.

The Invoker

						
							public class SimpleRemoteControl {
								Command slot;

								public SimpleRemoteControl() {}

								public void setCommand(Command command) {
									slot = command;
								}

								public void buttonWasPressed() {
									slot.execute();
								}
							}
  • This is the Customer: The only piece of code that knows about both the Command and the Receiver at once.
  • Line 3: The remote is our Invoker, it will be passed a command object that can be used to make requests.
  • Line 4: We create a light object, which will be the Receiver of the request.
  • Line 5: We create a LightOnCommand and pass the Receiver to it.
  • Line 7: We pass the command to the Invoker in setCommand.
  • Line 8: And then we simulate the button being pressed.
  • If Vendor #8 ships SecurityControl with arm()/disarm(), what has to change?
  • Command — no. SimpleRemoteControl — no.
  • You write one new class, SecurityArmCommand implements Command, and you're done.
  • SimpleRemoteControl depends on the Command abstraction, never on the concrete vendor type; that's the Dependency Inversion Principle.

Delivering the Full Request

Now that we have turned methods into objects, we can do other things too.

  • Undo a command
  • Queue up a large set of commands
  • Log a sequence of commands
  • Many receivers can undo their action
  • undo() is not automatic — the ConcreteCommand author has to think through the true inverse of what execute() did.
  • For LightOnCommand, that's easy: call off().
  • It's not always this clean; a Cook's undo might be donate it to charity, or eat it himself.
  • Sometimes reversing an action requires real design judgment, not just a mirrored method call.

Undo

						
							public interface Command {
								public void execute();
								public void undo();
							}

							public class LightOnCommand implements Command {
								Light light;
								public LightOnCommand(Light light) { this.light = light; }
								public void execute() { light.on(); }
								public void undo() { light.off(); }
							}
  • Commands can pile up faster than the system processes them.
  • Queue them and work through the backlog when it can.

Logging Commands

  • The Invoker keeps a List<Command> of everything executed.
  • Prior to executing a specific Command object, add the object reference to the list.
  • Enables undoing a whole sequence, or replaying after a crash.
